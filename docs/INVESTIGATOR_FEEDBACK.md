# HUMAN-IN-THE-LOOP INVESTIGATOR FEEDBACK

## 1. Overview & Objective

The **Human-in-the-Loop (HITL) Feedback** system allows investigators, crime analysts, and domain evaluators to provide direct, structured assessments of the behavioral matches generated by the CRIME DNA engine.

After reviewing an analysis—such as a similarity comparison, incident simulation, or pattern association—the user can quickly evaluate its operational utility:

```text
Was this behavioral match useful?
👍 Yes     👎 No

Optionally identify which aspects were useful / relevant:
☑ Similar time
☑ Similar location
☑ Similar property
☐ Similar method
☐ Other

[ Optional operational notes (no PII) ]
[ Submit Feedback ]
```

---

## 2. Ethical Transparency & Model Retraining Disclaimer

> ### **CRITICAL SCIENTIFIC PRINCIPLE: EVALUATION ONLY**
> **For the hackathon MVP, user feedback is stored strictly as evaluation and validation data.**
> 
> - **No Automatic Retraining**: Feedback does **NOT** automatically update, fine-tune, or retrain the underlying machine learning models (Spherical K-Means $k=8$, KNN cosine similarity index, Isolation Forest).
> - **Integrity & Anti-Poisoning**: Autonomous online retraining on unvetted user inputs risks catastrophic forgetting, feedback loops, and data poisoning. Feedback is safely preserved for offline validation, human-reviewed benchmarking, and future supervised calibration.
> - **Explicit User Disclosure**: The user interface and API responses prominently communicate this constraint:
>   > *"Feedback is recorded strictly for human-in-the-loop evaluation and system validation. It is not currently utilized for automatic model retraining."*

---

## 3. Data Minimization & Privacy Protection

In compliance with data protection and privacy-by-design principles:
1. **Zero Personally Identifiable Information (PII)**:
   - The feedback system never requests, stores, or logs investigator names, email addresses, badge numbers, device identifiers, or IP addresses.
2. **Minimal Storage Footprint**:
   - Stores only the minimum required evaluation metrics:
     - `feedback_id`: Unique anonymized record key (e.g. `FB_A1B2C3D4E5F6`).
     - `created_at`: UTC timestamp.
     - `is_useful`: Boolean (True for 👍 Yes, False for 👎 No).
     - `target_type`: Context label (`"incident_analysis"`, `"similarity_explanation"`).
     - `target_id`: Optional non-PII incident ID or scenario title (e.g. `"INC_136975"`).
     - `useful_aspects`: Array of selected behavioral dimensions (`["similar_time", "similar_location"]`).
     - `notes`: Sanitized optional operational comment (max 500 characters, no PII allowed).

---

## 4. Evaluated Behavioral Aspects

Investigators can specify which behavioral dimensions of the Behavioral DNA representation were operationally relevant:

| Aspect Key | UI Label | Operational Meaning |
| :--- | :--- | :--- |
| `similar_time` | Similar time | Temporal execution match (e.g., nocturnal hours, day of week, seasonal timing). |
| `similar_location` | Similar location | Setting and spatial context match (e.g., small-city, suburban, residential dwelling, commercial retail). |
| `similar_property` | Similar property | Economic target match (e.g., property category, forced entry, damage scale). |
| `similar_method` | Similar method | Modus operandi & weapon context match (e.g., unarmed stealth, weapon brandishing). |
| `other` | Other | Unique behavioral traits or contextual factors not captured in the primary categories. |

## 5. Storage Architecture

Feedback data is stored redundantly and atomically using standard, dependency-free storage:

1. **SQLite Database (`data/feedback/feedback.db`)**:
   - Structured table `investigator_feedback` with indexed columns for fast aggregation and statistical queries.
   ```sql
   CREATE TABLE IF NOT EXISTS investigator_feedback (
       feedback_id TEXT PRIMARY KEY,
       created_at TEXT NOT NULL,
       is_useful INTEGER NOT NULL,
       target_type TEXT,
       target_id TEXT,
       useful_aspects TEXT,
       notes TEXT
   );
   CREATE INDEX IF NOT EXISTS idx_fb_useful ON investigator_feedback(is_useful);
   ```

2. **Append-Only JSONL Audit Log (`data/feedback/feedback.jsonl`)**:
   - Human-readable, append-only log enabling trivial export to pandas, BigQuery, or external analytical tooling.

## 6. API Endpoints

### 6.1 Submit Evaluation Feedback
```http
POST /api/feedback
Content-Type: application/json

{
  "is_useful": true,
  "target_type": "incident_analysis",
  "target_id": "INC_136975",
  "useful_aspects": ["similar_time", "similar_location", "similar_property"],
  "notes": "Strong alignment on nocturnal residential break-in characteristics."
}
```

## 7. Frontend Component: `FeedbackWidget`

The `FeedbackWidget` is implemented in `frontend/src/components/FeedbackWidget.tsx`:
- **Discreet Initial State**: Displays only the question *"Was this behavioral match useful?"* with tactile `👍 Yes` and `👎 No` buttons.
- **Progressive Disclosure**: Selecting an option smoothly expands the aspect checkboxes and optional notes field.
- **Immediate Confirmation**: Shows a clean confirmation message reminding the investigator that feedback is recorded for evaluation.
- **Integration Points**:
  - Embedded in **Incident Simulator / Analysis** (`InputAnalysisPage.tsx`) directly after scenario results.
  - Embedded in **Why Similar?** (`WhySimilarPage.tsx`) directly below the mathematical similarity explanation card.

## 8. Automated Testing & Verification

The feedback subsystem is verified by `tests/test_investigator_feedback.py`:
- `test_submit_positive_feedback`: Verifies valid payload submission, ID generation, and disclaimer.
- `test_submit_negative_feedback`: Verifies negative evaluation handling with notes.
- `test_aspects_sanitization`: Verifies that unauthorized aspect keys are safely filtered out.
- `test_feedback_summary_statistics`: Verifies calculation of positive rates, totals, and dimension breakdowns.
- `test_storage_files_integrity`: Asserts that SQLite tables and JSONL audit logs persist correctly.
